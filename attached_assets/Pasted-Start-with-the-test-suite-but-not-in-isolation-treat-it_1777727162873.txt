Start with the **test suite**, but not in isolation—treat it as a **stabilization gate** for everything else.

If you skip this and jump to OAuth or admin features, you’re effectively deploying blind. Given how much logic you’ve centralized in services (scoring, feeds, auth), even a small refactor can introduce **silent data corruption** (especially in XP, idempotency, or feed ranking).

---

# 🎯 Recommended Execution Order (Tight, Realistic)

## **1. Fix Test Suite → Establish CI Gate (Day 1–2)**

This is your **force multiplier**.

### Why first:

* Protects scoring system (high complexity + easy to break)
* Validates feed logic before you simplify it
* Ensures auth changes (OAuth) don’t regress

### What to do (practical, not idealistic):

**Step 1: Stop trying to “fix everything”**

* Identify failing test categories:

  * Service tests (likely constructor mismatch)
  * Repository tests
  * Integration tests

**Step 2: Patch constructor drift quickly**

* Update test setup to match current service signatures
* If needed, introduce **TestConfig factory methods** instead of duplicating constructors everywhere

**Step 3: Ruthless triage**

* If a test is:

  * Outdated AND low-value → delete it
  * Complex but important → rewrite minimally

👉 Goal is not perfection. Goal is:

> “CI passes and covers critical paths”

### Minimum coverage targets:

* Auth flow (JWT issuance/validation)
* ScoreEventLog idempotency
* Ship creation
* Feed retrieval (at least one path)

---

## **2. Fix GitHub OAuth (Same Day or Next)**

This is your **entry point to the product**.

Use GitHub OAuth app:

### Critical checks:

* `VITE_GITHUB_CLIENT_ID` (frontend)
* `GITHUB_CLIENT_ID` + `GITHUB_CLIENT_SECRET` (backend)
* Redirect URI matches exactly
* CSRF state stored in Redis and validated

👉 Test full flow:

```
Login → Callback → JWT → Access protected endpoint
```

Without this, nothing else matters.

---

## **3. Basic Admin & Moderation Layer (Day 2–4)**

Don’t overbuild this.

### You only need:

#### Backend

* `User.role = ADMIN`
* Annotation guards:

  ```java
  @PreAuthorize("hasRole('ADMIN')")
  ```

#### Admin APIs

* Delete ship
* Ban user (soft delete or flag)
* View reported content

#### Minimal DB additions:

* `reports` collection:

  * reporterId
  * targetId
  * type (SHIP/COMMENT)
  * reason
  * status

#### Frontend (keep it ugly)

* `/admin`
* Table view:

  * Users
  * Ships
  * Reports
* Buttons:

  * Delete
  * Ban

👉 This is not a product feature. It’s a **safety valve**.

---

## **4. Multibase Fallback (Day 4–5)**

Right now you have a hidden outage risk.

### Add simple fallback:

* Primary: Multibase
* Secondary: S3-compatible (or even local disk for now)

Use:

* Circuit breaker pattern
* On failure → fallback storage

👉 Even a crude fallback is better than silent failure.
